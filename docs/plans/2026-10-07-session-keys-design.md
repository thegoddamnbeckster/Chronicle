# Session keys — design and API audit

**Status:** Built 2026-10-07. Deviations from the original design are listed in §9.
**Replaces:** the stateless 24-hour JWT used by the web UI.
**Does not change:** API keys (`X-API-Key`) used by Kodi, scrobblers and the ABS bridge.

---

## 1. Why

Today a login returns a JWT, valid for 24 hours and signed with a secret saved in
`keys\jwt.secret`. The server keeps no record of it. Consequences:

- Restarting the API does not end a session: the same secret validates the same token.
  The persistence was added on purpose (Program.cs comment: a fresh secret per boot "would
  silently log out every user"). The product requirement is now the opposite.
- Logout is client-side only. The token stays valid until it expires.
- A user's role is copied into the token at login, so demoting an admin takes up to 24 hours to
  take effect. (Deactivation already works, through `DeactivatedUserCache`.)
- The server cannot list or end a user's sessions.

**Requirement (owner, 2026-10-07):** login makes Chronicle generate a session key and return
it. The user may act only while holding a valid key, checked on every request. One key per
active session, several allowed per user. When the API restarts, all keys are invalid and
everyone logs in again.

---

## 2. Design

### 2.1 The key
- 32 bytes from `RandomNumberGenerator`, base64url, prefixed `chr_sess_` so it is recognisable
  in a secret scanner and cannot be confused with an API key (`chr_live_…`).
- Opaque: carries no claims. All facts about the session live on the server.
- Generated by Chronicle only, and only after a successful password check. There is no
  pre-login key, so session fixation is not possible.

### 2.2 The store
`ISessionStore`, a singleton, in memory:

| Field | Purpose |
|---|---|
| `SessionId` (GUID) | Public identifier for listing and revoking. Never the key. |
| `KeyHash` | SHA-256 of the key; the dictionary key. The raw key is never stored. |
| `UserId` | Owner. |
| `CreatedAt`, `LastSeenAt` | Idle timeout and display. |
| `AbsoluteExpiresAt` | Hard cap regardless of activity. |
| `ClientInfo` | User-agent (truncated to 200 chars) and remote IP, for the sessions list. |

- SHA-256 is enough here (not bcrypt): the key has 256 bits of entropy, so there is nothing to
  brute-force, and a fast hash keeps the per-request cost negligible.
- **Memory-only is the feature.** Nothing is written to disk, so a restart, crash or container
  restart empties the store and everyone logs in again.
- The interface is small (`Create`, `Validate`, `Touch`, `Revoke`, `RevokeAllForUser`,
  `ListForUser`) so a database- or Redis-backed store could replace it if Chronicle ever runs
  more than one instance. Single instance is a stated assumption (§7).
- Cap of 20 live sessions per user; creating the 21st evicts the least recently seen.
- A background sweep (every 5 minutes) removes expired entries.
- **Background polling and the idle timeout.** The web UI polls on its own (`NowPlayingBanner`,
  `AuthFailureContext` every 60 s, and later the change feed and notifications). Left naively,
  an open tab would keep a session alive forever and the idle timeout would only fire when every
  tab is closed. Polling requests therefore send `X-Chronicle-Background: 1` and do **not**
  advance `LastSeenAt`; only requests the user triggers do. They are still authenticated and
  still rejected once the session expires. A tab someone walked away from therefore expires
  after the idle period even while it keeps polling.

### 2.3 Expiry
- **Idle timeout:** `auth.session_idle_hours`, default 24. Every valid request moves
  `LastSeenAt`.
- **Absolute lifetime:** `auth.session_max_days`, default 30.
- Both are `app_settings` (no hardcoding), editable by an admin.

### 2.4 Authentication on every request
A new `SessionAuthenticationHandler` (scheme `"Session"`) replaces JwtBearer:

1. Read `Authorization: Bearer <key>`. No header → `NoResult` (so the API-key scheme can try).
   A bearer value that does not start with `chr_sess_` (for example a leftover JWT from before
   the upgrade) also fails cleanly as 401, never as a server error.
2. Hash, look up, reject if missing or expired.
3. Load the user's **current** state (`IsActive`, `IsAdmin`, username) from an in-memory user
   snapshot cache — the generalisation of `DeactivatedUserCache`, refreshed whenever
   `UserService` changes a user. Reject inactive or deleted users.
4. Build the principal from that live state, in the same claim shape as today
   (`NameIdentifier`, `Name`, `Role`) plus a `chronicle:session_id` claim. Controllers do not
   change. Role changes now apply on the next request.
5. Touch `LastSeenAt`.

The default authorization policy accepts the `Session` and `ApiKey` schemes, as it accepts
JWT and `ApiKey` today. `[Authorize]` and `[Authorize(Roles="Admin")]` keep working unchanged.

The `Authorization: Bearer` header name is kept so the web client's request code does not
change.

### 2.5 Endpoints
| Endpoint | Auth | Behaviour |
|---|---|---|
| `POST /api/v1/auth/login` | none | Verifies credentials, creates a session, returns `{ token, user }`. |
| `POST /api/v1/auth/register` | none | See §6, F-4. Returns the same shape. |
| `POST /api/v1/auth/logout` | session | Revokes the calling session. |
| `POST /api/v1/auth/logout-all` | session | Revokes all of the caller's sessions, including this one. |
| `GET /api/v1/auth/sessions` | session | The caller's sessions (id, created, last seen, client info, `isCurrent`). |
| `DELETE /api/v1/auth/sessions/{id}` | session | Revokes one of the caller's own sessions. Another user's id returns 404. |
| `GET /api/v1/users/{id}/sessions` | Admin | A user's sessions. |
| `DELETE /api/v1/users/{id}/sessions` | Admin | Revokes all of that user's sessions. |

`AuthResponse.token` keeps its name to avoid churn in the web client; the value is now a
session key. (Rename to `sessionKey` in a later, separate change.)

Session-management endpoints reject API-key authentication: only a real login manages
sessions.

### 2.6 Revocation triggers
| Event | Effect |
|---|---|
| Logout | That session ends. |
| Self password change | All of the user's *other* sessions end; the current one stays. |
| Admin password reset | All of that user's sessions end. |
| Password-reset token used | All of that user's sessions end. |
| Deactivate or delete a user | All sessions end; the snapshot cache also rejects them if one slips through. |
| Role change | No revocation needed; the next request sees the new role. |
| API restart | Everything ends (empty store). |

### 2.7 Web client
Almost unchanged, which is the benefit of keeping the header:
- `LoginPage` / `RegisterPage` keep storing the returned `token` in `localStorage`
  (`chronicle_token`) and `client.ts` keeps attaching it.
- A restart produces a 401 on the next request; `client.ts` already clears the token and
  redirects to `/login`.
- Add a Logout action that calls `POST /auth/logout` before clearing local state.
- Add an "Active sessions" panel to Settings → My Profile (list, end one, end all others), and
  per-user "end sessions" on Manage Users.
- Multiple tabs in one browser share one key (same `localStorage`). Logging out in one tab
  makes the others 401 on their next request. A second browser or device is a second session.
- Known wart: `client.ts` treats *any* 401 as "session expired", including a wrong password on
  the login form, which reloads `/login`. Fix while here: skip the redirect when the request
  was `/auth/login`.

### 2.8 Removal
- `JwtTokenService`, `IJwtTokenService`, the JwtBearer registration, `Security:JwtSecret`,
  `Security:JwtExpirationHours`, and the `keys\jwt.secret` handling in Program.cs.
- Existing browser tokens simply fail validation on first use and the user logs in again.
- The `keys` directory stays: Data Protection keys and plugin-settings encryption use it.

## 3. Docker and restarts

- The store is memory-only, so a container restart is a full session reset by construction.
- Behind a TLS-terminating reverse proxy, HTTPS to the browser is mandatory (the key is a
  bearer credential). Document that, and send `Strict-Transport-Security` when the request
  arrived over HTTPS (honouring `X-Forwarded-Proto` only from configured trusted proxies).
- Restore/restart (see the backup design) uses the same "ask the host to restart" interface:
  exit with a dedicated code; `restart: unless-stopped` in Docker, service recovery on Windows,
  the dev script otherwise.

---

## 4. Alternatives considered

| Option | Verdict |
|---|---|
| Keep JWT + per-boot ID claim | Fixes restart only. No logout, no session list, role changes still lag. Rejected. |
| Server sessions in the database | Survives restart, which is the opposite of the requirement. Kept as a possible store implementation for multi-instance. |
| Session key in an HttpOnly cookie | Better against XSS theft and would let `<img>` tags authenticate. Needs CSRF handling and a same-site API/web setup (the dev ports differ). Larger client change. Recorded as a future option, not chosen now. |
| Rotate the key periodically | Adds complexity (race between tabs) for little gain over idle and absolute expiry. Not now. |

## 5. Test plan

Unit: key format and entropy; hash-only storage; create/validate/touch/revoke; idle and
absolute expiry (with a fake clock); per-user cap eviction; revoke-all-for-user; sweep.

Integration (add alongside `AuthTests.cs`):
1. Login → call a protected endpoint → 200.
2. No header, malformed header, unknown key → 401.
3. Logout → the same key now 401.
4. Two logins → two distinct keys, both valid; ending one leaves the other valid.
5. Rebuild the host (new `WebApplicationFactory`) → the old key is 401. This is the restart
   test.
6. Self password change → other sessions 401, current session 200.
7. Admin reset, deactivate, delete → that user's sessions 401.
8. Demote admin → admin-only endpoint 403 on the very next request.
9. Idle expiry and absolute expiry (clock injected).
10. An API key still authenticates after the store is cleared, and cannot call the session
    endpoints.
11. `GET /auth/sessions` shows only the caller's sessions; `DELETE` of another user's session
    id returns 404.
12. The raw key never appears in logs (assert on captured Serilog output).
13. A polling request with `X-Chronicle-Background: 1` does not move `LastSeenAt`; a normal
    request does; and after the idle period a background request is rejected.
14. A leftover JWT as the bearer value returns 401 (not 500).
15. Restoring a backup (swapping the user table) then restarting leaves no sessions valid.

Update `AuthTests`, `ApiTokenTests`, `DeviceAuthTests` and the other integration suites that
mint JWTs through a test helper to use the new login flow.

## 6. API audit (2026-10-07)

### 6.1 Who authenticates how

| Client | Credential | Affected by this change? |
|---|---|---|
| Web UI (React) | JWT in `localStorage`, `Authorization: Bearer` via `client.ts` interceptor | **Yes** — becomes a session key |
| Chronicle_Scraper (Kodi addon) | API key, `api_key` setting, obtained through device auth | No |
| Chronicle_Scrobbler addon | API key (same device-auth flow) | No |
| Chronicle_Rating addon | Reuses the Scrobbler's API key | No |
| ABS metadata-provider bridge | `X-API-Key` header | No |
| ABS scrobbler service | `X-Api-Key` header, `POST /api/v1/scrobble` | No |
| SIMKL_Scrobbler | Talks to SIMKL's API only; no Chronicle calls found | No |

So the migration touches `AuthController`, `Program.cs`, the web client and the tests only. No
Kodi or bridge change.

### 6.2 What the web client sends and receives
- Every Axios call goes through the interceptor in `src/api/client.ts`, which attaches
  `Authorization: Bearer <chronicle_token>` when present. ✔
- Two direct `fetch` calls exist: `/api/v1/themes` (anonymous by design — needed to theme the
  login page) and `/api/health` (anonymous, readiness poll). Neither needs a credential. ✔
- Two `<img src>` uses, which cannot carry headers: `/api/v1/media/{id}/local-poster` and
  `/api/v1/media/poster-proxy?url=…`. Both are `[AllowAnonymous]` for that reason (see F-2).
- A 401 anywhere clears the token and redirects to `/login`. Correct for this design (see the
  login-form wart in §2.7).
- `AuthFailureContext` polls `/plugins/auth-failures` every 60 s and `DeviceAuthPage` checks the
  token's presence only; both keep working.

### 6.3 Endpoint authorization map
Controllers with a class-level `[Authorize]` (so every action requires a session or API key,
with `[Authorize(Roles="Admin")]` on the admin actions): ApiTokens, BackgroundTasks,
Duplicates (Admin), Enrichment, FileScan, Filesystem, Import, KodiDevice, Library, Media,
MediaLists, People, Plugins, Reports, ScanFolder, Scraper, Scrobble, Settings, Stats, Sync,
Users.

Anonymous on purpose or by necessity:

| Endpoint | Why | Verdict |
|---|---|---|
| `POST /auth/login`, `POST /auth/register` | Entry points | See F-4 |
| `GET /api/health`, `GET /health` | Readiness | OK |
| `GET /themes` | Themes the login page | OK |
| `POST /device-auth`, `GET /device-auth/{code}/poll`, `GET /device-auth/{code}/qr` | Kodi pairing before it has a key | OK; confirm codes are short-lived and rate-limited |
| `GET /plugins/{id}/icon` | `<img>` | OK (id only, served from registry) |
| `GET /media/{id}/local-poster` | `<img>` | Acceptable; id only |
| `GET /media/poster-proxy?url=` | `<img>` | **Unsafe — F-2** |
| `GET /media/overrides/reset-progress` | Progress poll | Should require auth — F-3 |
| `GET /filescan/status`, `/import-progress`, `/progress` | Progress polls | Should require auth — F-3 |
| `GET /diagnostics` | **No attribute at all** | **Unsafe — F-1** |

### 6.4 Findings

These were noticed during the audit and are independent of the session change. They are listed
here so they are not lost; none has been fixed yet.

- **F-1 — `GET /api/v1/diagnostics` is unauthenticated.** `DiagnosticsController` has no
  `[Authorize]`. It returns the repo root, API directory, database path and size, log path,
  git branch and commit, ports and version to anyone who can reach the server. Fix: add
  `[Authorize]` at minimum (the UI already calls it with a session); consider `Admin` only.
- **F-2 — `GET /api/v1/media/poster-proxy?url=` is an anonymous, unrestricted proxy.** It
  fetches any http/https URL the caller supplies and streams the response back with the
  upstream content type. That allows server-side request forgery against `localhost` and the
  LAN (for example `10.0.0.x` devices or the Chronicle API itself), and makes Chronicle an open
  relay that can serve arbitrary content types from its own origin. Fix: allow only image
  content types, cap the size, block loopback/private/link-local addresses after DNS
  resolution (and on redirects), and ideally replace the URL parameter with an item id so
  Chronicle only fetches URLs it already holds.
- **F-3 — Progress endpoints are anonymous.** `filescan/status`, `import-progress`,
  `progress` and `media/overrides/reset-progress` leak scan paths and activity to unauthenticated
  callers. They are plain XHR calls, so they can require a session with no client change.
- **F-4 — Registration is open, unthrottled.** `POST /auth/register` creates an account for
  anyone who can reach the server; only the first user becomes admin. There is also no
  rate limiting on `/auth/login`. Fix: `auth.allow_registration` setting (default off once the
  first user exists; admins create accounts from Manage Users), and .NET's built-in rate
  limiter on login (per IP and per username, with backoff).
- **F-5 — API keys carry the owner's full privileges.** An API key belonging to an admin
  authenticates as an admin: a leaked Kodi device key could call user-management and other
  admin endpoints. Fix (follow-up): give keys a scope (for example `scrobble`, `scraper`,
  `full`) and have the API-key handler apply it; deny session-management and user-admin routes
  to scoped keys.
- **F-6 — Role changes lag up to 24 h today.** Fixed by this design (§2.4).
- **F-7 — Logout does not end a session.** Fixed by this design.

## 7. Assumptions and limits
- Single API instance. Scaling out needs a shared store behind `ISessionStore`.
- Sessions are lost on any process restart, including crashes. This is intended.
- The key lives in `localStorage`, so an XSS bug on the web origin could steal it. The cookie
  alternative (§4) would reduce that; revisit if third-party content is ever rendered unsafely.
- HTTPS is required in any deployment reachable beyond localhost.
- Server-side logs must record `SessionId`, never the key. Checked: the Serilog request logger
  (Program.cs) logs method, path, status, remote IP and user-agent only, not headers, and the
  key is never in a URL, so nothing leaks today. Keep it that way; the test plan asserts it.

## 8. Implementation order
1. `ISessionStore` + tests.
2. User snapshot cache (generalising `DeactivatedUserCache`) + tests.
3. `SessionAuthenticationHandler`, policy wiring, login/logout endpoints + integration tests.
4. Revocation hooks in `UserService` (password change/reset, deactivate, delete).
5. Web: logout, sessions panel, login-401 fix.
6. Remove JWT code and config; update docs (`SECURITY.md`, `API_SPECIFICATION.md`).
7. Fix F-1 to F-3 (small, independent — can ship first), then F-4 and F-5.

## 9. As built (2026-10-07) — deviations and decisions

- **User state is read from the database on every request**, not from a snapshot cache (§2.4
  step 3). A primary-key projection is cheap on local SQLite and removes a whole class of
  stale-cache bugs. `DeactivatedUserCache` stays as a no-DB fast reject.
- **Named policies, not `AuthenticationSchemes` on the attribute.** ASP.NET *merges* an
  `[Authorize(AuthenticationSchemes=...)]` attribute with the default policy, so it would still
  have accepted an API key. Session-only routes use `AuthPolicies.SessionOnly` /
  `SessionAdmin` (found by a failing test).
- **Registration stays open** (decision, 2026-10-07): the first user becomes administrator and
  grants admin to others, as before. F-4 is therefore reduced to login throttling, still open.
- **Poster proxy** now requires a session; the web client fetches it through the API client and
  shows a blob URL. The fetch also refuses private/loopback/link-local/metadata destinations
  (checked at connect time, so DNS rebinding and redirects are covered), non-image content, SVG,
  and anything over 10 MB.
- **Logging** is `AuthAudit` (logger context `Chronicle.Auth`): login/register success and
  failure, logout, session revocations, and rejected session/API keys (throttled to one line per
  minute per source+reason+key tag). The old JWT config (`Security:JwtSecret`,
  `JwtExpirationHours`) and `JwtTokenService` are removed; an existing `keys\jwt.secret` file is
  now unused and can be deleted.
- F-1 (diagnostics), F-2 (poster proxy) and F-3 (progress endpoints) are fixed and covered by
  `EndpointExposureTests`.
- Still open from the audit: login throttling (rest of F-4), API-key scopes (F-5), the remaining
  anonymous `local-poster` and plugin-icon image routes (id-only; acceptable for now), and
  confirming device-pairing codes are rate-limited.

## 10. Follow-up hardening (2026-10-07, same day)

Closed the items section 9 left open:

- **Login and registration throttling** (`LoginThrottle`): per (address, username), per address and
  per username; limits in `app_settings`; 429 + `Retry-After`; refused before the password is
  checked. A unit test caught that the first version blocked everyone (a `FirstOrDefault` on a
  struct returned a default value whose `Allowed` was false).
- **API-key scopes** (`ApiKeyScopes`, `ApiKeyScopeHandler`, migration `AddApiTokenScope`). Scoped
  keys are never administrators. Existing keys stay `full` so no Kodi box or bridge can break;
  QR pairings from now on are `device`. Key management, session management and pairing approval
  require a login.
- **Device pairing**: starts, unknown-code guesses and the number of unexpired codes are limited.
- **Image routes** (`local-poster`, plugin icon) require a login: an HttpOnly SameSite=Strict
  session cookie, accepted only by those routes, replaces anonymous access.
- **Forwarded headers**: `Security:TrustedProxies` limits who may claim an address; the audit log
  also shows the real peer.
- **Audit logging** is now an injected service (`AuthAuditLog`) instead of a static with a test hook.
- **Poster proxy fetcher** is an instance with an injectable address filter and DNS resolver, so its
  network behaviour (content type, size, redirects, DNS rebinding) is tested against a real server.
- **Settings** for all the limits are read through `CachedAppSettings` (stale-while-revalidate), so
  no request waits on the database and a change applies within about a minute.

Deliberately left as is: the per-request user lookup in the session handler (one indexed
primary-key SELECT; it guarantees a demoted or deactivated user is refused on the very next
request, which a cache would make eventually-consistent), and the scan progress endpoints, which
need only a login like the rest of the scan controller.

Plugin icons: `plugins/{id}/icon` now fetches the manifest URL through `SafeImageFetcher` (https
only, 100 KB, private/loopback/metadata destinations refused including on redirects and after DNS)
instead of a plain named HttpClient, which was removed. SVG is still rasterised to PNG and
magic bytes still checked before anything reaches a browser. All eleven real plugin icon URLs were
checked: their content types are within what the fetcher accepts.
